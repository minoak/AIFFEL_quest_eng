# FSDL 01 — Day 1. 전략과 기획

## Chapter 0. Introduction

### 평평한 지구 ML vs 둥근 지구 ML
- **평평한 지구 ML**: ML 워크플로우를 직선으로 본다. 모델이 좋은 성능을 내면 "프로젝트 끝"으로 간주. 끝(종착점)이 있는 관점.
- **둥근 지구 ML**: 끝이 없다. 배포가 종착점이 아니라 새로운 시작점. 한 바퀴 돌아 다시 출발점으로 이어지는 순환 구조.
- **데이터 플라이휠(Data Flywheel)**: 이 순환을 굴리는 엔진. 사용자 → 실제 데이터 유입 → 더 나은 모델 → 더 많은 사용자 → 더 많은 데이터. 한번 돌기 시작하면 관성으로 가속되는 무거운 바퀴처럼, 데이터가 쌓일수록 제품이 강해지는 선순환.
- 비유: 배포는 평평한 지구에서의 "종착점"이지만, 둥근 지구에서는 외부 루프(Outer Loop)의 "시작점"이다.

### 세 과정의 범위 구분 (Ch 0 체크포인트 1)
- **모델 배포 개론** (FastAPI/Streamlit): 완성된 모델을 사용자에게 전달하는 인터페이스에 집중.
- **Full Stack DL** (본 과정): 모델의 생애 전체를 관리하는 엔지니어링 사고방식. "그 모델이 올바른 문제를 푸는가, 데이터는 신뢰할 수 있는가, 재현 가능한가"를 의심.
- **MLOps** (다음 과정): 그 사고방식을 실제 인프라로 구현. Docker로 환경 격리, GCP에 파이프라인, 자동화/CI-CD.

## Chapter 1. ML 제품의 가치

### Software 1.0 vs 2.0 (Ch 1 체크포인트 1)
- **Software 1.0**: 사람이 규칙(if-else 로직)을 직접 명시. 입출력 관계를 사람이 정의.
- **Software 2.0**: 데이터로부터 규칙(파라미터)을 학습. 최적화 알고리즘(경사하강법)이 데이터를 바탕으로 코드를 '작성'.
- **핵심 기준**: 복잡도가 아니라 **"규칙을 누가 정하느냐"**.
  - 선형 회귀처럼 단순해도, 파라미터(w, b)를 데이터가 학습했으면 → 2.0
  - 1000줄짜리 복잡한 룰베이스라도, 사람이 다 짰으면 → 1.0
- 내 경험 대입: Belladonna의 Lua 규칙 엔진 = 1.0 (호감도 임계값 등 모든 규칙을 직접 작성). 파인튜닝한 Gemma 모델 = 2.0 (데이터로 가중치 형성).
- 딥러닝이 "가장 2.0다운 2.0"인 이유: feature 선택조차 모델이 스스로 함.

### CACE 현상 (Ch 1 체크포인트 2)
- **CACE = Changing Anything Changes Everything**: 하나를 바꾸면 전체가 바뀐다.
- **전통 소프트웨어(1.0)에서 덜 문제인 이유**: 값이 바뀌어도 **예측 가능하게, 국소적으로** 바뀐다. diff로 추적 가능하고 원하면 롤백. (예: Lua에서 `호감도 > 80`을 `> 70`으로 바꾸면, 정확히 그 구간만 영향받고 추적 가능)
- **ML 시스템(2.0)에서 치명적인 이유**: 무엇이 바뀔지 모른 채 **전역적으로, 예측 불가능하게** 바뀐다. (예: temperature 0.7 → 0.8 하면 어디가 어떻게 바뀔지 미리 못 짚고, 상관없어 보이는 출력까지 흔들림)
- 결과: ML은 부분 테스트/격리가 안 되어 기술적 부채가 빠르게 축적됨 → MLOps의 필요성.

## Chapter 2. ML 도입 결정

### Build vs Buy vs API (Ch 2 체크포인트 2)
- **단기 = API 우선**: 검증 안 된 아이디어에 처음부터 자체 모델 학습(GPU/데이터/수개월)을 투입하지 말 것. API로 빠르게 만들어 "사람들이 쓰나"부터 검증. ("당신은 구글이 아니다")
- **판단 기준은 "주력 서비스냐"가 아니라 "API가 못 하는 구체적 이유가 있느냐"**:
  - 자체구축이 맞는 경우: ① API로 안 되는 제어가 필요 (특정 화풍/캐릭터 일관성/세밀한 워크플로우 — 내 ComfyUI 경험이 정확히 이 예시) ② 규모가 커져 API 호출 비용 > 자체 운영비 ③ 데이터 보안/외부 의존 제거
  - API가 계속 맞는 경우: 일반적인 작업이면 상용 API가 자체 학습보다 압도적으로 좋을 가능성 높음
- 의사결정 순서: ① API로 되나? → ② 안 되는 구체적 이유가 있나? → ③ 그 이유가 자체구축 비용을 정당화하나?

# FSDL 02 — Day 2. 인프라와 데이터

## Chapter 8. PyTorch → PyTorch Lightning

### 전통 PyTorch 루프의 한계
잘 돌아가지만 규모가 커지면 손으로 감당 불가:
- GPU 1 → 4개로 늘면 학습 코드를 대대적으로 다시 써야 함 (데이터 분할, 그래디언트 평균, 동기화 직접 구현)
- 학습 중 서버가 죽으면 → 체크포인트 없으면 처음부터
- 실험 100번 돌리면 어떤 하이퍼파라미터가 어떤 결과였는지 추적 불가

### 체크포인팅의 진짜 의미
- 모델 가중치만 저장하면 부족. **옵티마이저 상태 + 에포크 번호 + 스케줄러 상태**까지 저장해야 진짜 "이어서 학습" 가능.
- 이유: Adam은 파라미터마다 momentum/variance 누적 상태를 가짐 → 이걸 안 살리면 옵티마이저가 "기억상실"에 걸려 학습이 삐끗. 에포크 번호 없으면 스케줄러가 학습률 위치를 잊음.

### 실험 관리 (W&B)
- 실험 수십~수백 개의 하이퍼파라미터/결과를 주피터 메모로 관리하는 건 확장 불가능.
- **Weights & Biases**: 학습 시 하이퍼파라미터+결과를 자동 기록, 대시보드로 비교/시각화. GPU 사용률 등 시스템 메트릭도 자동 수집.

### Lightning의 핵심 철학: 3분할 (Ch 8 체크포인트 1)
"관심 있는 부분(본질)은 내가, 관심 없는 부분(잡일)은 도구에 위임."

| 상자 | 담당 | 들어가는 것 |
|---|---|---|
| **LightningModule** | 모델 본질 (무엇을 계산하나) | 모델 구조, forward, loss 정의(training_step), 옵티마이저(configure_optimizers) |
| **LightningDataModule** | 데이터 | 다운로드(prepare_data), 전처리/분할(setup), DataLoader(train_dataloader) |
| **Trainer** | 실행 환경 (어떻게/어디서 돌리나) | GPU/CPU, 분산, 정밀도, 체크포인트, 로깅 |

- 본질(loss 정의)은 LightningModule. 하지만 **역전파(backward)/가중치 업데이트(step)는 Trainer가 자동 처리** — loss를 return만 하면 됨. (전통 PyTorch의 `zero_grad → backward → step` 3종 세트가 사라짐)
- 전처리는 Trainer가 아니라 **DataModule**로 분리 (모델/환경과 별개인 "데이터" 축).
- 전환 시 사라지는 코드 5가지: `.to("cuda")`, `optimizer.zero_grad()`, `loss.backward()`, `optimizer.step()`, 메트릭 수동 집계(`val_loss_sum += ...`)

### "한 줄로 바뀌는" 엔지니어링 (본질 코드 불변)
```python
trainer = pl.Trainer(accelerator="auto", devices=1)              # 환경 자동
trainer = pl.Trainer(accelerator="gpu", devices=4, strategy="ddp")  # GPU 4대
trainer = pl.Trainer(precision="16-mixed")                       # 혼합정밀도
```
- **혼합정밀도(Mixed Precision)**: 계산은 16비트로 빠르게, 가중치 업데이트만 32비트로 정밀하게. 메모리 절반 + 속도 ~2배인데 성능은 거의 유지. "공짜 점심에 가장 가까운 것." → 잡일이므로 Trainer 소관 (16/32비트는 "모델이 뭘 학습하나"를 안 바꿈)

### 분산 학습: DDP vs FSDP (Ch 9와 연결)
거대 모델 학습 시 메모리 문제부터 이해해야 함:
- **모델 메모리 = 가중치 + 그래디언트 + 옵티마이저 상태**
  - 4B 모델이면 가중치 ~16GB지만, 그래디언트 +16GB, Adam 옵티마이저 상태 +32GB → 학습엔 파라미터의 3~4배 메모리
  - OOM의 흔한 진범은 모델이 아니라 **옵티마이저 상태** (내 Gemma 4B 파인튜닝에 ~40GB 필요했던 이유)
- **DDP (Distributed Data Parallel)**: 데이터를 나눔. 각 GPU에 모델 전체 복사 + 데이터 배치만 분할 → 그래디언트 평균. 모델이 GPU에 들어갈 때 "빠르게". (어제 배운 부하분산처럼 "완전한 복사본 여러 개")
- **FSDP (Fully Sharded Data Parallel)**: 모델을 나눔(샤딩). 가중치/그래디언트/옵티마이저 상태를 조각내 각 GPU에 분산 → 모델이 GPU 하나에 안 들어갈 때. (부하분산과 다른 점: 어떤 GPU도 혼자선 전체 모델을 못 가짐 → GPU 간 통신 필수)
- 선택 기준: **먼저 DDP, 안 들어갈 때만 FSDP** (FSDP는 조각 주고받는 통신 비용 큼)
- 연결: 양자화(압축) vs FSDP(분산) — 둘 다 거대 모델을 메모리에 욱여넣는 목표지만 접근이 정반대. 실무에선 병행.

### PyTorch와 Lightning의 관계 (중요 개념)
- Lightning은 PyTorch를 **대체하지 않음**. PyTorch **위에 얹힌 층**(그릇/내용물 관계, WSL-우분투와 동일 구조).
- LightningModule 안의 `nn.Module`, forward, loss는 전부 PyTorch 문법 그대로. Lightning은 반복 껍데기(for 루프, .to, backward)만 걷어냄.
- **그래서 PyTorch부터 배운 이유**: 토대를 알아야 그 위 도구를 제대로 쓰고, 문제(NaN, 그래디언트 안 흐름) 발생 시 원인을 짚을 수 있음.
- LLM 학습 도구 계층: PyTorch(토대) → Lightning / HuggingFace Trainer / DeepSpeed·Megatron(그 위 도구들). 전부 PyTorch 기반. "PyTorch가 LLM에 쓰인다"와 "Lightning이 있다"는 모순 아님 — Lightning은 PyTorch를 쓰는 한 방식.
